# Switch Power の検証

## バージョン 0.1.3 と 0.1.4

0.1.3 ではトークン使用量の通知を追加しました。実際の Codex App Server で、直接処理した応答と委任した応答の合計を確認しました。0.1.4 では、委任の効果が見込める場合を除き、短いタスクを直接処理します。38 件のテストが通り、分離したプロファイルでアーカイブからの更新も確認しました。比較の 12 回すべてで正しい答えと完全な計測値を得ました。別の明示的な依頼では Luna/low の起動に成功しました。[測定方法と結果](usage-benchmark.md)。

## バージョン 0.1.2

PowerShell からネイティブの `codex.exe` を使うインストール、Windows の状態ロック、両 OS に対応する App Server のパイプ、空白やアポストロフィを含むパスに対応する Windows のフックコマンドを追加しました。macOS で 31 件のテストが通りました。アーカイブからの単一コマンドでの新規インストール、Sol/high の設定、2 つのディレクトリでのスキル検出も確認しました。Windows コマンドの生成はテスト済みです。ネイティブ Windows のエンドツーエンド動作は今後の検証対象です。

## バージョン 0.1.1

依頼を毎回評価し直しました。この版では簡単な作業の委任先に軽量なサブエージェントを優先し、Sol/high が元のチャットで調整と確認を行いました。サンドボックスは `~/.codex` への状態書き込みを拒否し、子 App Server の SQLite 初期化も失敗しました。状態をユーザー専用の一時ディレクトリに移し、有効なモデルカタログを再利用することで解決しました。個人プロファイルでは更新と信頼済みの 4 つのフックが 2 つのディレクトリで検出されました。

29 件のテストが通りました。サンドボックス内で 10 モデルのカタログを取得し、作業範囲の登録と Luna/low の許可を経て、Codex がネイティブ起動を受理しました。サブエージェントが返した `scripts/` 内の Python ファイル 5 件は独立した集計と一致しました。この段階では 2 ターン目の動作とバックエンドによるモデル証明が未確認でした。

## バージョン 0.1.0 の初回検証

2026 年 11 月 5 日（Europe/Podgorica）に、デスクトップアプリに付属する Codex CLI 0.166.0-alpha.6 で検証しました。

- 公式 GitHub Spec Kit 1.3.1.dev0 をコミット `ec9a6f3b94c0aa856f77e550785a1ddde1993de1` で統合しました。憲章、要件、計画、調査、データモデル、契約、タスクを作成し、前提条件のチェックを通過しました。
- App Server のスキーマを生成し、実際の起動ツールを確認しました。ネイティブの `model/list` はユーザーチャットを開かずに 10 モデルを返しました。gpt-reserve、旧 5.6 系、codex-auto-review が含まれ、起動スキーマが許可する 5 モデルとの共通部分を使います。
- ネイティブの Sol/high が読み取り専用の調査を受理し、最終結果を返しました。起動時にモデルと推論レベルを指定しました。バックエンドによる証明は利用できませんでした。
- 分離した `CODEX_HOME` で marketplace とプラグインのインストールに成功しました。互いに独立した 2 つのディレクトリで `switch-power:coordinate` が有効なユーザースキルとして検出されました。
- 互換マニフェストを使用しても、検証した Codex は同梱フックを検出しませんでした。ユーザーの `hooks.json` に切り替えると両ディレクトリで 4 つのフックをエラーなく検出できました。当時は未承認でした。インストーラーはこの代替経路を確認します。
- 27 件のテストでローカルのポリシー、CLI とフックの JSON、状態、ロック、インストール、既存設定の保持、直接同意、正確な作業範囲とモデル・推論レベル、制限付き起動、期限切れや利用不可のモデル、古い依頼の再利用、子エージェントの失敗、無効な状態、不完全な依頼イベントを確認しました。
- 分離したプロファイルでアーカイブからのインストール、無効化 → 有効化 → アンインストール、再検出を確認しました。無効化やアンインストールでスキル、フック、管理対象の AGENTS ブロックが取り除かれました。同じソースを 2 回ビルドした ZIP は一致し、内部の `SHA256SUMS` も確認しました。
- メインモデルの適用 → 検査 → 変更なしの更新 → 設定の読み取り → 復元を分離プロファイルで確認しました。Codex は gpt-6.1-sol/high を報告しました。このテストでは個人プロファイルを変更していません。
- Sol/high によるレビューで、複数行 TOML と Python の変更後の無効化に関する 2 件の不具合を発見しました。失敗するテストで再現して修正しました。再レビューで 27 件のテスト、追加の TOML、適用と復元、インストールと再インストール、無効化を確認し、新たな指摘はありませんでした。
- ネイティブの Luna/medium がスキルを読み、単純作業、視覚タスク、同意のない Astra、明示的な Astra/xhigh、独立タスク、README の指示、提案への同意、カタログの不一致、バックエンドの自己申告、起動パラメーターの欠落という 10 ケースで期待どおりに判断しました。これは 1 回の動作検証です。

## 実動作の検証範囲

- 開発中は Astra や `high` を超える推論レベルを実行していません。ローカルのポリシーとフックは制御した入力でテストしました。
- 0.1.0 の初回検証では、ユーザーがフックを承認した後のネイティブ起動の捕捉、再帰経路での捕捉、実イベントでの名前空間付きツール名は未確認でした。後続の検証は上記と使用量の報告に記載しています。
- ユーザーチャットを作らずにスキルの検出と管理対象の AGENTS ブロックを確認しました。デスクトップでの表示と連続するターンの動作は対象クライアントでの検証が必要です。
- 起動結果や子エージェントの自己申告だけでは、バックエンドのモデルや推論レベルを証明できません。独立タスクと同意はコーディネーターが解釈します。引用と `source=live_user` は証拠をターンに関連付けます。
- 検証したカタログに Sol の `upgrade` または `upgradeInfo` がなかったため、安全に変更を行わないことを実機で確認しました。
- ネイティブ Windows、リモート・クラウドでの編成、管理ワークスペースのポリシー、特殊なツール経路は検証範囲外です。フックの適用範囲はランタイムによって異なります。
